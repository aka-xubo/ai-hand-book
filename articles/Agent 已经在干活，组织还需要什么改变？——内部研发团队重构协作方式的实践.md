# Agent 已经在干活，组织还需要什么改变？——内部研发团队重构协作方式的实践

> 本文根据原文整理为 Markdown。涉及内部团队、人员、平台、链接和截图数据的信息已匿名化或模糊化处理。

# 洞察

> - **团队 AI 化的分水岭，不是有多少人在使用 Agent，而是 Agent 的工作能否沉淀为组织资产。** 当上下文和结果停留在个人会话中，Agent 只是个人工具；只有进入共享任务、协作分工和质量反馈，才可能形成组织能力。
> - **AI 提效不能只优化汇报环节，而要改变事实产生和沉淀的方式。** 晨会总结失败说明，事后让 AI 拼接碎片信息无法还原工作全貌；有效上下文必须伴随任务执行持续形成。
> - **人机协作需要统一的是任务上下文，而不是工作工具。** 人、Agent、Jira、协作工具和 Codex 可以分布在不同系统中，只要讨论、执行、反馈和结果始终围绕同一任务闭环。
> - **引入 协作平台，不是因为 Jira 无法存储上下文，而是因为 Jira 的协作模型仍以人为中心。** 协作平台 补上了 Agent 的身份、分工、协作与治理能力，让 Agent 从外围工具进入任务协作本身。
> - **Agent 的自主上限，本质上取决于组织自身的“可执行程度”。** 1.6% 的独立完成率说明，真正限制 Agent 的不只是模型能力，更在于业务知识是否清晰、结果能否自动验收、执行边界是否明确。

# 背景

> ***当 Agent 已经参与执行，团队应该怎样重构协作方式，才能让个人借助 Agent 获得的效率，成为团队可以共享和复用的能力？***

过去一段时间，Agent 已经真实进入我们的工作。在 Codex、Claude Code 等工具中，Agent 可以分析需求、修改代码、执行测试、整理文档。

但我观察到一个反差：**大家使用Agent普遍很熟练，个人工作的速度已经变快，团队整体效率却似乎没有发生太大变化。**

# 一次失败的提效实践

> **怎样让一项工作的背景、判断、讨论、进展和结果，在执行过程中持续归位**

内部研发团队 原来每天都开晨会。大家轮流同步昨天做了什么、今天准备做什么、当前有什么问题，Leader 再从中识别风险、追踪异常。既然会议可以转录，AI 也能分析文本，一个自然的想法是：把晨会内容交给 AI，让它自动总结整理，帮助我们管理日常工作。

真正尝试后，我们发现事情没有这么简单。说得直接一点，**AI 整理出来的是一堆看似完整、实际无法使用的信息垃圾**：

![内部示意图（已脱敏）](assets/agent-team-collaboration/01-morning-report-problem.png)

内容看起来很多，却回答不了我们真正关心的几个问题：**这究竟是什么事，为什么要做，现在到了哪一步，谁在负责，接下来要做什么。**

为了继续推进，我一度让成员在晨会结束后补录背景信息。但这很快暴露出一个悖论：**原本我希望 AI 减少大家的汇报负担，结果为了让 AI 看懂，团队反而多了一项工作。**

![内部示意图（已脱敏）](assets/agent-team-collaboration/02-context-entry-problem.png)

这次失败的根本问题在于**晨会中的信息天然是碎片化的。AI 缺少一项工作从发生到现在的连续上下文。晨会只提供了某个时点的若干片段，它不是任务本身，也无法独立还原任务的全貌。**

> **那么 “团队现有的工作系统中，哪里已经沉淀了这些上下文？”**

# Jira：团队已有的任务上下文来源

> **Jira 可以为 Agent 提供任务的目标和边界，并把相关讨论、历史、状态和结果串联起来。**

我们首先想到的是 Jira。团队长期使用 Jira，团队日常工作中的一部分重要上下文，本来就已经沉淀在其中：一项任务为什么产生、讨论过哪些方案、做过什么判断、当前进展如何、最终怎样处理。

成员查找相似问题、分析问题原因或接手历史任务时，也一直在依赖这些信息。**Jira 不只是任务流转系统，也是团队已有的任务上下文来源。**

此前，我们已经设计过一个颇受欢迎、并持续迭代的 Jira Skill。它最初只负责读取单条 Jira 任务，让 Agent 获得一项具体工作的背景、状态和历史记录，而不必再由人临时整理和转述。

这带来了一个直接变化：**人不再需要先把 Jira 中的信息重新“翻译”给 Agent，只需要提供任务编号，Agent 就可以从已有上下文开始工作。**

这也让我们确认了一个方向：**与其在工作结束后让 AI 从会议和汇报中拼凑事实，不如让人和 Agent 从一开始就围绕明确的任务及其上下文开展工作。**

> **既然 Jira 能够提供任务上下文，它是否也适合成为未来人和 Agent 共同协作的工作现场？**

# Jira 的限制：Agent 难以进入协作内核

> **Jira 可以提供任务上下文，却难以承载人和 Agent 共同工作的协作关系。**

![内部示意图（已脱敏）](assets/agent-team-collaboration/05-jira-collaboration-limit.png)

*既然 Jira 已经承载了大量任务上下文，那我们为什么不围绕 Jira 做配套好了？*

**在信息连接层面，这条路是可行的。** 通过 Jira API，我们可以读取和更新任务、写入字段与评论，也可以在外围开发协作工具机器人、同步服务和 Agent Skill。

**但 Jira API 能够扩展数据，却很难从外围重构 Jira 原有的协作模型。** **Jira 的核心关系仍然是“人负责一项任务”**。Agent 可以读取和写回信息，却很难在系统中作为“**一等公民**”。

**于是，我们的选择是Jira退居幕后，引入一个新的协作层：协作平台（基于开源协作框架打造）。**

# **协作平台：让 Agent 长在协作现场里**

> **一个从设计之初就把 Agent 视为协作主体的工作系统**

![内部示意图（已脱敏）](assets/agent-team-collaboration/06-collaboration-platform-architecture.png)

- **以任务为锚点，用Issue作为人和 Agent 共同工作的最小场域。**

- Issue 承载任务背景、讨论记录、关键判断、执行过程和最终结果，让不同的人和 Agent 能够围绕同一项工作持续接力。

- **把Agent 设计成 “一等公民”**

- Agent 是谁？ -- 身份信息、所属团队、工作状态、任务可分配

- Agent 如何参与工作？ -- @agent、读取上下文、回填上下文

- 人如何保持控制？-- 观察、纠正、接管、追溯

![内部示意图（已脱敏）](assets/agent-team-collaboration/07-issue-list.gif)

- **“沟通在哪里，执行就在哪里”**
当人在 Issue 中提出问题、补充约束或作出决策时，不需要再把这些内容重新整理并复制给 Agent。Agent 就在当前协作现场中，可以基于已经形成的上下文直接开始工作。

![内部示意图（已脱敏）](assets/agent-team-collaboration/08-issue-detail.gif)

# 一个真实的“人—Agent—Agent”协作示例

> **一个真实的线上案例：人、`Agent`、`Agent` 协作闭环**

![内部示意图（已脱敏）](assets/agent-team-collaboration/09-human-agent-loop.png)

- **任务始于Issue**

- **读取 Issue 上下文：**我们仍然在自己熟悉的 Codex 中工作。只需要提供 Issue 编号，Codex 就可以通过 Skill 读取其中的需求背景、讨论记录、约束条件和当前进展，并据此分析和执行任务。

- **Issue 阶段性汇报回填，并唤起线上 Agent 同事：**完成一轮开发后，Codex 通过Skill 把本轮完成内容、关键判断和验证结果回填到 协作平台，并主动在 Issue 中 `@Code Review Agent`。

- **线上Agent 参与审查，补充结论**：Code Review Agent 被唤起后，会读取同一条 Issue 的任务上下文和 Codex 刚刚回填的执行记录，对本次改动进行审查，并把问题和修改意见写回 Comment。

- **下一轮循环**：Codex 随后读取审查意见（需要人类唤起，非主动），修改代码、完成验证、再次回填，并重新唤起 Code Review Agent。如果审查仍未通过，这个过程会继续循环，直到任务完成。

![内部示意图（已脱敏）](assets/agent-team-collaboration/10-review-loop.gif)

# 一个月后的我们

> **一种围绕共享任务上下文展开的人机协作方式，已经能够在真实团队中持续运行，并开始改变信息同步和任务协作习惯。**

## 一些数据和事实

- 内部研发团队 的工作已经 **100% 围绕 协作平台 展开**：平台累计 608 个 Issue，其中 498 个已完成；。**晨会和周报先后取消**，协作工具群中的**进度询问和背景补充也明显减少，平台内累计形成 1,476 条沟通记录。**

- **Agent 仍处于早期参与阶段**：线上 Agent 任务参与率为 **13.3%**，独立完成率只有**1.6%。**

## 内部实践看到的变化

- 任务上下文开始**从个人记忆变成团队可以共享的工作基础**

- Agent 开始**从个人工具，变成团队可以分工、观察和接力的协作主体**

- 管理开始**从维护信息流，转向设计协作规则**

# 结语：方向已经出现，真正的挑战刚刚开始

> **从 Human in the Loop 走向 Human on the Loop，关键是让 Agent 能理解业务、独立执行、自证结果，并始终处于人的监督之下。**

- **这仍然是一次早期实践。**10个人，大概1个半月，不足以证明这套协作方式能够复制到更大的团队、跨部门协作和非研发场景。

- 目前，Agent 已经可以读取上下文、接受任务、执行工作、回填结果，并与其他人或 Agent 协作。但线上 Agent 的任务独立完成率仍然只有 1.6%。这说明，**把 Agent 接入协作流程，只解决了“Agent 能不能参与”的问题，还没有解决“人能不能从具体执行中抽离”的问题。**

- *无论使用协作平台、Jira，还是其他协作平台*，要让人从 Human in the Loop 逐步转向 Human on the Loop，都需要补齐**三个基础条件**：

- **业务领域知识、本体** -- 是否知道做什么、怎么做

- **任务能够自动验收 -- 是否知道已经做对**

- **执行边界足够清晰 -- 是否知道什么时候必须停下来找人**

![内部示意图（已脱敏）](assets/agent-team-collaboration/16-agent-autonomy-conditions.png)

> 下一阶段，我们会围绕三个方向继续验证：
> - **构建业务知识基础**：从已有代码和架构知识继续向**业务领域知识、本体**、规则与例外扩展，让 Agent 不只理解代码，也能理解为什么做。
> - **建立自动验收闭环**：把需求逐步转化为机器可执行的验收条件，让 Agent 能根据验证结果继续修改，而不是每轮都等待人工判断。
> - **明确 Agent 的执行边界**：在平台中定义哪些任务可以自动执行，让 Agent 从简单的、可控的任务开始。
> 我们会把这些能力放进真实任务中持续运行，并关注两个结果：
> - **Agent 独立且高质量完成任务的比例是否提高**
> - **团队从需求到交付的链路是否缩短。**
